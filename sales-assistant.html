Conversational assistant over enterprise sales data

Solution Lead and developer · national wholesale distributor · 2025 – 2026

Problem

A national wholesale distributor's sales team had years of order and account history available to them, and a reporting interface to reach it. In principle anyone could get an answer. In practice, getting one meant knowing which filters to set, setting several of them correctly, and then waiting for the results to load.

The predictable result: people stopped asking questions they would have benefited from asking. The data was accessible and effectively unused.

Solution

An assistant that takes a question in plain English and returns an answer from the same data. Underneath, it combines SQL generation against the structured records with retrieval over supporting material, so it can handle both "what did this account order last quarter" and questions that need context the database alone does not carry.

Access control was a first-class requirement, not a later addition. Row-level security means the assistant only ever answers from the accounts a given person is entitled to see, and the same question from two people can correctly return two different answers.

What I owned

  • Named Solution Lead in the signed statement of work, co-leading delivery.
  • Built the assistant itself, the permissions model, and the knowledge base behind it, with a small team.
  • Delivered a cloud migration, the row-level security implementation, knowledge base expansion, and input validation.
  • Onboarding and integration into the platform the sales team already worked in.

Stack

Python, SQL generation combined with retrieval-augmented generation, role-based and row-level access control, ERP integration, Azure.

What was interesting

Row-level security in a retrieval system is harder than it looks. In a normal application the permission check happens at the query. Here, a model composes the query, and separately a retriever pulls documents that may themselves contain restricted figures. Both paths have to be constrained, and the constraint has to survive a user who asks an indirect question. Getting that right meant treating permissions as part of retrieval rather than a filter applied after.

The second lesson was about adoption. A tool like this succeeds only if the answers are trustworthy enough that people stop double-checking them in the old interface. That put more weight on validation and knowledge-base quality than on the conversational surface, which is the part everyone notices first.
